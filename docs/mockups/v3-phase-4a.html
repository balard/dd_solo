Run screen mockups

v3 Phase 4a. Every screen a run adds, drawn at the three sizes v2 measured: the start screen with a run on it, the race pick, the force between encounters with the next enemy in view, the reward of five, an event, a battle inside a run, and the run's end. The run is one Treefolk run in Act II, at encounter 5 of 12, against Coral Elves. Every die is a real die with its real faces from data/. The decisions are in PLAN-V3.md, under What 4a found.

Measured: does each screen fit, and is its answer in reach?

Every view and variant at every size, rendered offscreen. Fits means no scrolling at all; otherwise the overflow is how far the page scrolls. The answer (Fight, Take, Upgrade, Start) sits in a footer that never scrolls, so it is always in reach; the question is how much of the screen above it the player has to scroll through to judge it.

What the frames decide

The act strip

  • Three acts, the current one wide. A slot per encounter: a green square won, a diamond an event, a ring where you are, a hollow dot ahead. Ahead is a dot and never a kind: encounters are drawn as they are reached, so the strip does not know.
  • The current act names its cap, which is the one number the force is built against.
  • Phone upright: the current act only, one line and a row of small pips. Done and coming acts are words.
  • On every run screen but the battle, where the header names the encounter instead.

The force between encounters

  • The next enemy is at the top, dice and all: enemyForce answers at arrange_force, and you build against what you will meet.
  • Then the builder, over the run's pool and cap. Spare dice are the palette, and a die won since the last battle says new.
  • Fight is a footer that never scrolls. Disabled, it names the first problem beside it, and every problem also sits beside its section.
  • Leave run is in the footer too, never in the way of Fight.
  • On a short screen (a phone sideways) the enemy's dice start folded and terrain and dragons fold to one line with Change: 1.9 screens of scrolling became 1.3.

Rewards and events

  • An offer is the die: its tile, its name, and every face in a row. A tap opens the inspector, as on the board.
  • Pick, then Take: the footer names the pick ("Take Eldar Dryad"). One tap never spends the reward.
  • An event picks a die from the pool first, then says what each choice does to it: Upgrade names the result and whether it stays fielded, Transform lists all four it might become.

The battle, and the end

  • The game screen, unchanged, with the encounter in the header and two buttons: Leave run (comes back to this battle's start) and Concede, which asks and says it ends the run.
  • The game-over card leads on: "Pick your reward" after a win, "See the run" after a loss.
  • The run's end is a page of its own: how far, the encounters in order, the force that fell. Shown once, then the save is cleared.

What the run does not know yet

  • Its history. The act strip's past slots, the end page's encounter list, its counts and the new marks all need what happened at each encounter, and RunState keeps only this act's drawn ids. 4b adds a history, and with it the first RUN_VERSION bump.
  • What an upgrade would do before it is chosen: stay in place, wait in the pool, or leave the force. That is replaceDie's rule, so it is a query in src/run/, never a second copy in a component.
